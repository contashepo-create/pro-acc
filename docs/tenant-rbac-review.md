## 1) الفصل بين الشركات (Tenant Isolation) — ✅ سليم

- **مصدر الحقيقة هو قاعدة البيانات:** `requireApiAuth` يجلب `company_id` و`role` و`token_version` من جدول `users` بالاعتماد على `userId` المُستخرَج من التوكن (وليس من التوكن نفسه). فلا يمكن لعبث التوكن تغيير الشركة/الدور.
- **كل استعلامات البيانات مقيّدة بـ `.eq('company_id', ...)`:** فحص برمجي شامل لكل مسارات API للبيانات (projects, invoices, vouchers, journal, boq, clients, suppliers, accounts, cash, banks, ...) أظهر **صفر** نقاط تسريب عبر الشركات.
- **واجهات المستخدمين داخل الشركة** (`/api/company/users`) تتحقق دائماً من أن المستخدم المستهدف ينتمي لنفس الشركة قبل القراءة/التعديل/الحذف، مع قيود إضافية:
  - منع تغيير دورك الخاص أو تعطيل حسابك.
  - **مدير نظام واحد فقط لكل شركة** (منع ترقية مستخدم ثانٍ إلى admin لتفادي تجاوز الصلاحيات).
  - منع حذف آخر مدير نشط.
- **إدارة الصلاحيات** تتحقق من انتماء المستخدم لنفس الشركة في GET/POST، ومسار DELETE مقيّد بـ `company_id` فلا يمكنه لمس صفوف شركة أخرى.
- **لوحة المطور (Zerocold)** محمية بصلاحية `superadmin` منفصلة.

> ملاحظة على RLS: الجداول مفعّل عليها RLS لكن سياساتها «افتراضية لكل شيء» (`USING true`) لأن التطبيق يستخدم `service_role` الذي يتجاوز RLS، والانعزال الفعلي يتم في طبقة التطبيق (المؤكَّد سليماً). **توصية:** تحويل هذه السياسات إلى قواعد `USING (company_id = auth.uid() ...)` بحيث تصبح طبقة دفاع ثانية إن استُخدم مفتاح anon مستقبلاً.

## 2) نظام الصلاحيات — المنطق سليم ✅

`lib/permissions.ts` يعمل بثلاث طبقات:
1. **الأدوار الافتراضية** (admin كامل، manager واسع، accountant إنشاء/تعديل بلا حذف/موافقة، supervisor قراءة فقط).
2. **صلاحيات مخصصة لكل مستخدم** في `user_permissions` تتجاوز/تقيّد الدور (والقائمة الفارغة `[]` تحظر الوحدة تماماً).
3. **admins دائماً مصرَّحون** دون بحث في قاعدة البيانات.

`hasModulePermission` يتحقق من (userId, companyId, module, action) مع عزل تام.

## 3) ثغرة إنفاذ الصلاحيات — تم اكتشافها وإصلاحها 🛠️

### المشكلة
كانت **54 مسار API للبيانات** تستخدم `requireApiAuth` (مصادقة فقط = أي مستخدم داخل الشركة) بدلاً من `requireModulePermission` (مصادقة + تحقق صلاحية الوحدة/الإجراء). النتيجة:
- يستطيع مستخدم بدور `supervisor` (قراءة فقط) **إنشاء/تعديل/حذف** بنود الكميات، قيود، فواتير مرحلية، مصروفات مشاريع، مبيعات POS، أصول، عقود، مناقصات، سندات، عُهد، إلخ.

### الإصلاح
حوّلت جميع المسارات الكتابية (POST/PUT/PATCH/DELETE) في هذه الـ 54 مساراً إلى `requireModulePermission(request, module, action)` مع تحديد الوحدة والإجراء الصحيح لكل مسار:
- أضفت وحدات جديدة إلى سجل `MODULES` (credit_notes, contracts, tenders, bonds, equipment, timesheets, petty_cash, budgets, branches, cost_centers, crm, gantt, pos, approvals, tax_returns, messages).
- عمليات حساسة خُصِّصت لها إجراءات دقيقة: الإغلاق/إعادة الفتح المالي واعتماد العُهد → `approve`، الإهلاك → `update`.
- مسارات القراءة (GET) بقيت بمصادقة + قراءة (محتاجة فقط للتسجيل الدخول)، ويُستحسن ترقيتها لاحقاً إلى `read` لمزيد من الدقة.

النتيجة: **الآن كل عملية كتابة على البيانات تخضع لدور/صلاحيات المستخدم**، فلا يستطيع supervisor مثلاً حذف قيد أو إنشاء مبيعات.

## 6) توصيات مستقبلية
1. **تقوية RLS** في قاعدة البيانات (سياسات `USING company_id = ...`) كطبقة دفاع ثانية.
2. ترقية معالجات القراءة (GET) إلى `requireModulePermission(..., 'read')` لدقة أتم (تفرض `read` على كل وحدة).
3. إضافة مراجعة دورية عند إضافة أي مسار API جديد: قاعدة «لا مسار كتابة إلا عبر `requireModulePermission`».
